# Как выкатывать изменения

## Ветка от свежего main

Всегда от обновлённого `main` (`git checkout main && git pull`). Имя — по сути
правки: `feat/route-map`, `fix/brighter-watermark`, `fix/round-cake`.

## Коммиты

- **Одна атомарная правка — один коммит.** Задача, замечание ревью, фикс —
  каждый отдельно. Если работа разошлась на «модель», «CLI» и «документацию»,
  это три коммита.
- **Одна строка, без тела.** Никаких `Co-Authored-By` и упоминаний Claude.
  Хук в `.claude/settings.json` блокирует такой коммит.
- Типы conventional commits: `feat`, `fix`, `docs`, `chore`, `ci`, `perf`,
  `refactor`, `test`. От типа зависит номер версии, который поставит
  release-please: `feat` двигает минорную, `fix` — патч.
- Пишите, что изменение даёт читателю: `fix: drop the certificate watermark
  below the headline`, а не `правки в background.py`.
- pre-commit может переформатировать файл и уронить коммит — повторите ту же
  команду `git commit`, второй раз пройдёт.

Готовя коммит, добавляйте файлы прицельно (`git add <файлы>`): в рабочем
дереве почти всегда лежат собранные `dist/`, `map.png` и прочие артефакты.

## Пулл-реквест

`gh pr create` с телом, где сказано, что поменялось и почему именно так.
Если решение спорное (например, деталь пришлось подвинуть из-за геометрии) —
это пишется в теле PR, а не остаётся в голове.

Дальше:

1. `gh pr checks <N>` — дождаться всех пяти проверок: `Lint & types`,
   `Tests (py3.11|3.12|3.13)`, `Build print kit`.
2. Мержить `gh pr merge <N> --rebase --admin --delete-branch`.
   **Squash в репозитории запрещён**, ruleset на `main` требует линейную
   историю и пулл-реквест; `--admin` нужен, потому что обязательных проверок
   в ruleset нет, а ждать их всё равно надо.

## Релиз

Релизы делает [release-please](https://github.com/googleapis/release-please):
после мержа в `main` он открывает PR вида `chore(main): release 0.13.0`
с обновлённым `CHANGELOG.md`, `.release-please-manifest.json` и строкой версии
в `src/ubt_race_docs/__init__.py` (там стоит маркер `x-release-please-version`).

Выпуск:

1. `gh pr review <N> --approve`, затем `gh pr merge <N> --rebase --admin`.
2. Workflow `Release` собирает весь комплект и прикладывает к тегу.
3. **Проверить ассеты**: `gh release view v0.13.0 --json tagName,assets`.
   Их должно быть 12 — номера, грамоты, две расписки, таблица призовых,
   карта, шесть STL и zip со всем сразу.

### Известная заминка

CI на самих релизных PR иногда падает, не запустив ни одного джоба, — GitHub
пишет «likely failed because of a workflow file issue». Это не наша поломка:
`gh run rerun <id>` на том же коммите проходит зелёным. Проверять стоит, но
блокировать релиз этим не нужно.

## Что гоняет CI

`.github/workflows/ci.yml`: pre-commit целиком, pytest на трёх версиях Python
и полная сборка комплекта, включая STL — на раннере ставится свежий OpenSCAD
из AppImage (распаковкой, потому что FUSE на раннерах нет).

## Ревью

Пользователь просит ревью-циклы явно («сделай два круга ревью»). Цикл — это
перечитать собственный дифф свежим взглядом, найти настоящие проблемы
и починить их **отдельными коммитами**, по коммиту на замечание. Если ничего
не нашли — так и сказать, а не выдумывать замечание ради процесса.

В этом репозитории ревью особенно внимательно к трём вещам: цифры на печати
(влезает ли, читается ли), совпадение параметров модели с тестами и то, что
в коммит не попали собранные артефакты.
